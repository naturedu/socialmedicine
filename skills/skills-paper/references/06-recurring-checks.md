# 反复出错的核查点与问题闭环

用于投稿前审核、收到编辑技术核查或用户指出“之前已经改过、怎么还有出入”时。将相同根源的问题合并处理；不把旧稿的待核状态永久继承到已修正的新稿。

## 先确定核查对象

记录当前稿件身份、版本、目标期刊、文章类型及本轮编辑来信。用户指定的最新版优先，但仍核对其中的数据和图表是否属于同一版本。区别用户原话、编辑来信、实际文件内容、原始来源和旧助手解释；旧助手报告“已完成”不能替代打开文件核实。

同一项目已经提供、确认且未被更正的信息直接复用，并记来源位置；只对缺失、矛盾或适用范围变化的事实追问。跨项目的批号、作者顺序、资助和授权不能自动复用。

## 复发问题清单

| 类别 | 常见表现 | 核对依据与处理 | 修复后的复查范围 |
|---|---|---|---|
| 声明残缺 | 有伦理标题但缺委员会/适用研究；有注册号却无日期；模板还写“待补” | 按[声明核对](07-declarations.md)分项核实并写入实际稿件 | Methods、Declarations、标题页、补充、回复信和系统中相同字段 |
| 日期混用 | 把注册日、批准日、入组日、检索截止日或 AI 使用日期当成同一日期 | 分清日期对象、事件及来源；编号恰似日期也不能据此解析批准日期 | 摘要、方法、登记信息、检索日志、研究背景检索和图注 |
| 伦理范围错接 | 只写原队列同意，却默认覆盖新二次分析；把匿名化直接写成伦理豁免 | 区分各项研究活动、数据访问条件及相应批准/同意依据 | Methods 与声明段的研究主体和时间范围 |
| 表格内容漂移 | 相同表格在不同稿件行数、分类、样本和数字不同 | 用稳定记录ID逐行比对，定位新增/删除/合并及其理由，不能只看总行数 | 主表、附表、结果段、摘要和图形数据 |
| 分析口径错配 | 研究数与报告数混用；患者与就诊次数混用；分子配错分母 | 明确分析单位、结局、时间点、模型与分析集；回查结果表具体行列 | 全文重复数字、流程图、图注和投稿信 |
| 统计意思变强 | OR 被写成风险变化；不显著被写成无效；相关被写成导致 | 保留效应类型、方向、区间及设计能够支持的解释 | 标题、摘要、结论、亮点和封面信 |
| 检索进度被写成完成 | 命中数当导出数；既有候选当最终纳入；只更新一库却写全库更新 | 分库核查执行记录、导出、筛选和未完成量；未执行不能填0 | Methods、PRISMA、摘要、Results、补充检索式 |
| PRISMA 只求算术闭合 | 为达到目标篇数补造排除数；未获全文混进全文资格排除 | 逐条决定与原因支持阶段汇总；区分记录、报告、独立研究及合成子集 | 流程图每个框、排除表、纳入表与Meta输入 |
| 背景检索混入主综述 | 更新引言文献后顺带改纳入范围；背景检索日期沿用主检索日期 | 把背景综述、首轮检索、扩展/更新检索分别记录 | Research in context、方法、引用和筛选表 |
| 方法完成状态不一致 | 正文写两位评价者完成质量评价，附录却写单人初评待复核 | 按实际执行记录写评价者、步骤和完成状态，不把计划改成已做 | 方法、结果、偏倚/证据分级表、摘要 |
| 引文身份与支持错位 | DOI能打开但题名不符；行重排后引用编号未同步；原文不支持论断 | 核对身份与具体支持位置；保留内部稳定ID再生成显示编号 | 文内引用、文后条目、表注、补充和文献管理库 |
| 图形任务与正文引用不符 | 分类图被用来证明时间趋势；概念图被当成因果证据 | 看图实际编码什么，再修正文句或提供支持该论断的结果图；用户要求保留的有效图不无故删除 | 图号、图题、图注、结果段和讨论 |
| 投稿规范串刊或串阶段 | 子刊补充要求被套到正刊主稿；别轮标红要求套到本轮 | 依据当前期刊、文章类型、本轮编辑来信，并标出适用文件 | 字体、篇幅、声明标题、清稿/标记稿、回复格式 |
| 改投残留 | 投稿信仍称原期刊；文章类型、日期、专题或刊名未更新 | 对当前目标刊逐字段检查；作者声明仍需适用于当前版本 | Cover letter、标题页、文件名、系统字段和回复抬头 |
| 表面修复而未落文 | 只给修改说明；Word改了但PDF仍旧；声明已改而系统摘要未变 | 打开最终文件核实修改位置，再查所有受影响载体 | 本地上传白名单、实际上传版本及可访问的系统字段 |
| 提交稿带工作痕迹 | AUTHOR TO COMPLETE、黄色待核、批注、修订者身份或旧图混入 | 工作稿保留审计线索；提交版消除占位但不靠删提示掩盖事实缺失 | Word正文/页眉页脚/属性、PDF、独立图、ZIP内容 |

这些是问题模式，不表示每篇稿件都存在这些问题。仅检查与本研究及本轮交付相关的项；无关项说明原因后跳过。

## 一项问题怎样才算结束

使用 `_checks/issue_log.csv`，或在已有工作台记录等价信息：

1. **定位**：问题ID、文件版本、页码/段落/表格行或系统字段，以及具体不一致之处。
2. **找依据**：原始材料、模型输出、作者已确认信息、官方页面或编辑来信；记清对象与适用范围。
3. **列影响**：哪些正文、图表、声明、补充或系统字段需要同步；未受影响的内容不重做。
4. **修复**：给出具体处理和新版本；没有事实依据时保留明确待核事项，不生成一个看起来合理的值。
5. **复查**：重新打开最终文件或实际字段，记录结果及证据位置；修改说明不等于修复证据。
6. **关闭/重开**：已解决且已复查才标 `CLOSED`。当相关数据、版本、作者事实或期刊要求变化时只重开受影响问题。

问题状态使用 `OPEN`、`NEEDS_AUTHOR`、`FIXED_PENDING_CHECK`、`CLOSED`；“已给建议”“已生成文件”不是自动关闭条件。阻断范围填写具体对象，如“伦理段与最终提交”，避免因一个字段缺失而停下整篇独立可做的工作。

无法访问投稿系统时可完成本地同步，将系统字段标为未查，提供待更新清单；不能把本地完成写成系统已更新。只有用户授权相应外部操作时才执行系统修改或提交。

## 交付核对结果

给出已修正问题、仍待作者事实、未执行的核查及当前版本。历史里没有频次统计时称“多次出现的类型”或“发现过的具体问题”，不要制造按次数排序的榜单。私人聊天索引和来信内容只留本地，公开技能只保留通用核查方法。
