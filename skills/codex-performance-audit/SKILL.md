# Codex 性能与指令审计

先区分输入/滚动卡顿、首个响应慢、持续思考慢、回答质量变化和单个工具等待。记录发生范围、客户端版本与一次可重复的操作；不要用技能文件大小推断界面故障。

用户请求客户端更新、缓存清理或旧聊天整理时，按需读取 [维护与清理](references/maintenance.md)。普通性能排查不自动扩大为删除、归档或软件升级。

## 只收集必要证据

- 用 `scripts/inventory.py --root <skills目录>` 统计技能入口和描述长度。输出只有数量和大小，默认不输出路径或正文。
- 本地核对当前模型、推理强度、可用内存和进程资源，以现场值为准，不沿用旧报告。本机默认配置不能证明网页模型或服务端路由。累计 CPU 时间不等于当前 CPU 占用；进程工作集之和也不是独占物理内存。
- 检查全局和项目指令、重复触发器、串行工具链、无条件读取、重复确认及默认多代理检查。技能正文通常按需加载，不能把磁盘总量称为每轮上下文量。
- 配置含私有路径和服务信息，只读取本次需要的字段。不要导出身份凭据、浏览器存储、原始会话或完整日志。

## 选择与验证

保持用户选择的模型、推理强度和服务档位。用户愿意用较少思考换取速度时，再针对具体任务调整；用户反映回答质量下降时，不默认降低推理强度，也不把缓存清理称为恢复模型能力。可能额外计费的提速需另有授权。

把冗长描述改成具体触发条件；把细分流程收进引用资料。合并入口前核对每个原能力仍可抵达；保留脚本、素材和原来源。不要只截断说明，也不要用上下文预算硬裁掉技能。

先备份本次会改动的文件，记录哈希；逐项改动并验证解析、引用和现有能力。重启或新会话后，用同一任务比较；未做对照就只报告配置/体积变化，不声称速度提升。数据库、缓存和会话不因体积大而直接删除。退出应用后才能进行确有依据的缓存修复。

参考当前[配置文档](https://learn.chatgpt.com/docs/config-file/config-reference)及[技能精简说明](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。应用版本和配置项应以现场支持情况为准。
